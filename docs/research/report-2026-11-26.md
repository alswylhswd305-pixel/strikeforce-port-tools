## Salem: sysmodule 0x003B
---------------------------------------------------------------------

### (1) What 0x003B is
- **KNOWN.** `0x003B` = `CELL_SYSMODULE_SYSUTIL_OSK_EXT`. This is the extended on-screen-keyboard (OSK) dialog utility, `/dev_flash/sys/external/libsysutil_oskdialog_ext.sprx`.
  - RPCS3 enum: `CELL_SYSMODULE_SYSUTIL_OSK_EXT = 0x3b,` → R/rpcs3/Emu/Cell/Modules/cellSysmodule.h#L74
  - RPCS3 module table: `{ .path = "external/libsysutil_oskdialog_ext.sprx", ... }, // CELL_SYSMODULE_SYSUTIL_OSK_EXT` → R/rpcs3/Emu/Cell/Modules/cellSysmodule.cpp#L139. The `MODULE_INFOS` array starts at index 0 on L80, and L139 − L80 = 59 = 0x3B.
  - ps3recomp's own header: `#define CELL_SYSMODULE_SYSUTIL_OSK_EXT 0x003B` → P/libs/system/cellSysmodule.h#L81
  - psdevwiki row "CELL_SYSMODULE_SYSUTIL_OSK_EXT | 0x003b | Extension of the on-screen keyboard dialog utility" → https://www.psdevwiki.com/ps3/User_talk:Euss/Libraries (also on https://www.psdevwiki.com/ps3/Talk:Error_Codes). These pages return 403 to curl, so I saw the row through the search index, not a live fetch.
  - The file exists in dev_flash → https://www.psdevwiki.com/ps3/Files_on_the_PS3

### (2) What the module exports
- **KNOWN.** RPCS3 registers it as library **`cellOskExtUtility`** → R/rpcs3/Emu/Cell/Modules/cellOskDialog.cpp#L1308-L1326 (`REG_FUNC(cellOskExtUtility, …)`).
- I computed the NIDs on the box with RPCS3's `ppu_generate_id`: SHA-1(name ‖ 16-byte suffix), first 4 bytes read **little-endian**. As a sanity check, the same script gives `cellSysmoduleLoadModule` → `0x32267A31`, which matches the value in ps3recomp's CHANGELOG (P/CHANGELOG.md#L823).

- **KNOWN.** ps3recomp has **no handler** for any of these. `rg "cellOskExtUtility|OskDialogExt|09565B21|1E1B4C97|E800F586|7EB292CD"` over the whole v0.20+ tree returned nothing. It does have the base `cellOskDialog` (P/libs/misc/cellOskDialog.c).
- **ASSUMED.** A game that loads 0x3B most likely calls the `Register…Callback` and `Set…` functions next (keyboard hook, force-finish callback, scale or colour). No source shows this. Every one of these Ext functions *takes* a callback or value and none *returns* a pointer per RPCS3's signatures (L1008-L1266). So a missing Ext handler alone should not hand the game a NULL function pointer. That makes it doubtful that 0x3B itself is the direct cause; it may just be the last log line before the crash.

### (3) Why the OPD/pointer is NULL: what ps3recomp actually does
- **KNOWN.** `cellSysmoduleLoadModule` in ps3recomp loads nothing. It records a flag and returns `CELL_OK` for any id < 0x100, including 0x3B → P/libs/system/cellSysmodule.c#L87-L101 (`sysmodule_slot` L17-L23). No PRX is loaded, and no import table is patched at that moment.
- **KNOWN.** Imports are bound at **lift time**: `ppu_lifter.py --hle-stubs` turns each import stub into `ps3_hle_call(nid)` → P/docs/GETTING_STARTED.md#L186-L199.
  - If `--hle-stubs` was missing, the call target would be `0x39800000`, the instruction `li r12,0`, not NULL (same doc).
  - So a **NULL** target does **not** match "lifted without --hle-stubs".
- **KNOWN.** For an NID with no handler, the default (`PS3_HLE_UNRESOLVED=ok`) sets **r3 = CELL_OK and writes no out-params**. It prints `[hle] UNRESOLVED NID 0x… -> faking CELL_OK` once per NID and dumps r3-r10 → P/runtime/ppu/ppu_hle.cpp#L195-L236.
  - The project itself documents this exact failure: unresolved imports fake success, a handle stays NULL, and the game later calls through it.
  - `YDKJ_NETOFFLINE`: "default r3=0 (fake success) → the game stores a NULL handle as an object and later virtual-calls it" → P/docs/DIAGNOSTICS.md#L1415.
  - `cellSpurs.c`: "returned CELL_OK without writing *size" → P/libs/spurs/cellSpurs.c#L3568.
  - gen_hle_nids.py: "the dispatcher's unresolved path answers CELL_OK with untouched out-params" → P/tools/gen_hle_nids.py#L93-L104.
- **KNOWN.** Valid PPU code lives at 0x10000..0x0FFFFFFF (game) or 0x30000000..0x3FFFFFFF (PRX) → P/docs/RUNTIME.md#L65 and P/runtime/ppu/ppu_loader.cpp#L3112-L3128.
- **ASSUMED.** An "OPD" at **0x7190** is *below* 0x10000, so it is probably not a real descriptor in the EBOOT. The likely pattern is `lwz rX, 0x7190(rBase)` with `rBase == 0`: a field at offset 0x7190 inside a **struct or object whose pointer is NULL**. Either an earlier HLE call faked success without filling that pointer, or the object comes from something never loaded. Unverified.
- **ASSUMED, alternative.** The game loads its **own** PRX (`USRDIR/*.sprx`) via `sys_prx_load_module` and calls through that PRX's exports. ps3recomp maps PRX syscalls to its HLE module registry (P/docs/SYSCALLS.md#L530-L536), so a game PRX that was not lifted (see P/docs/FIRMWARE_LLE.md, `tools/lift_prx.py`) would leave such pointers empty.
- **KNOWN, separate risk.** v0.20.0 shipped with merge losses that were fixed on master the next day: lwmutex FIFO hand-off, SPURS ctx-handler registration, and the Windows event-table lock. See commit 316be1d / PR #847 → https://github.com/sp00nznet/ps3recomp/commit/316be1d44ecb3ddc3a6ab77918dec12252343ce1 (reported in #843). This is not shown to cause this crash, but Salem should build from master ≥ e85647a rather than the v0.20.0 zip.
- **KNOWN, doc caveat.** ps3recomp's `docs/NID_SYSTEM.md#L44-L53` still says "4-byte suffix, big-endian". That is wrong. Use RPCS3's 16-byte suffix with a little-endian read (R/rpcs3/Emu/Cell/PPUModule.cpp#L58-L75 and P/CHANGELOG.md#L823).

### VERIFY (in order; all read-only)
1. **Is 0x7190 in the image?** Open `out/EBOOT.loader.json` / `EBOOT.image.json` from `ppu_loader.py` and check the segment ranges and OPD extent. If 0x7190 is outside every segment, H-NULL-object is very likely.
2. **What computes 0x7190?** Disassemble around guest address 0x0007C008+0xD30 = **0x0007CD38**:
   - `python tools/show_func.py 0x0007C008 --asm --max 0` (P/tools/show_func.py), or
   - `python tools/ppu_disasm.py EBOOT.ELF --va 0x0007CC80 --length 0x100`.
   - Look for `lwz r?,0x7190(rN)` / `lwz r0,0(r?)` / `mtctr` / `bctrl`, then walk backwards to find where `rN` came from: a load from a global, or the r3 / out-param of a preceding `bl` to an import.
3. **Which imports were faked right before?** Run the build with `PS3_HLE_TRACE=400` (logs nid, r3-r5, lr) and `PS3_CALLTRACE=200` (indirect calls) → P/runtime/ppu/ppu_hle.cpp#L413-L420, P/runtime/ppu/ppu_loader.cpp#L2814-L2817. Collect every `[hle] UNRESOLVED NID` line and match it against the table above and `python tools/nid_database.py --lookup 0xXXXXXXXX`.
4. **Which missing import is load-bearing?** Run once with `PS3_HLE_UNRESOLVED=fail` (P/runtime/ppu/ppu_hle.cpp#L209-L211); the game should stop on the first one that matters. Then `PS3_HLE_ARGS=<nid>` dumps r3-r10 for that NID.
5. **Ground truth from RPCS3.**
   - (a) Boot the same EBOOT in RPCS3 with Log Level = All, as the ps3recomp guide recommends (P/docs/GAME_PORTING_GUIDE.md#L64-L76). grep `RPCS3.log` for `cellSysmoduleLoadModule`, `cellOskDialogExt`, `sys_prx_load_module`, and any `.sprx` path. This shows which Ext calls happen and whether a game PRX loads.
   - (b) Use ps3recomp's RPCS3 oracle tools `tools/rpcs3_probe/probe.py`, `trace.py`, `rsp.py`. They drive RPCS3's GDB stub (`"GDB Server", "127.0.0.1:2345"` → https://github.com/RPCS3/rpcs3/blob/master/rpcs3/Emu/system_config.h#L394). Set a breakpoint at `0x0007CD38` and capture registers plus memory at `rBase` and `rBase+0x7190` → P/tools/rpcs3_probe/probe.py. In RPCS3, `rBase` should be a real object pointer; comparing it shows which call should have produced it.
   - ASSUMED: breakpoints need the PPU to run in the interpreter, or to stop at that address under LLVM. probe.py's docstring does not say; test it.
6. **Game PRX check:** list `PS3_GAME/USRDIR/*.sprx` in Saud's own dump (P/docs/GAME_PORTING_GUIDE.md#L125-L157).

### (4) Fastest documented ways to reach a first frame
- **KNOWN, band-aid.** `PPU_NOOP_BAD_VCALL=1` turns an indirect call to a misaligned or out-of-code-range target (anything < 0x10000, so NULL counts) into a no-op with r3=0. "Lets the boot proceed PAST bad vcalls (diagnostic band-aid — skipped methods leave state incomplete)." See P/docs/DIAGNOSTICS.md#L550 and P/runtime/ppu/ppu_loader.cpp#L3122-L3140. `PPU_VCALL_BT=1` prints a host backtrace for each one.
  - VERIFY: run with both set and see whether the next blocker comes before or after the first flip.
- **KNOWN.** Add per-game stubs in the template's `stubs.cpp` for the unresolved NIDs (P/docs/GAME_PORTING_GUIDE.md#L395-L410, P/docs/GETTING_STARTED.md#L380-L386). For the 17 `cellOskExtUtility` NIDs above, mirror RPCS3: return CELL_OK, and for Register* store the callback pointer. RPCS3's own versions are mostly `todo` + CELL_OK (cellOskDialog.cpp L1008-L1266).
  - ASSUMED: this is enough for these 17, since no source says the game reads their results.
- **KNOWN, pattern from shipped ports.** When a faked CELL_OK leaves a NULL handle, ports return a real **error** instead, so the game takes its graceful fallback path. Example: `YDKJ_NETOFFLINE` → P/docs/DIAGNOSTICS.md#L1415. A minimal real handler is also used, e.g. `YDKJ_SAVEDATA` (P/docs/DIAGNOSTICS.md#L1443).
- **KNOWN.** Regenerate the NID table with **all** modules (`gen_hle_nids.py --all`). A misspelled module name used to silently fake every NID of that module (P/tools/gen_hle_nids.py#L93-L104).
- **KNOWN.** No public Dynasty Warriors: Strikeforce port exists that I could find. A GitHub repo search for "strikeforce ps3" found only a save editor (https://github.com/alsharfa/Dynasty-Warriors-Strikeforce-ps3-save-editor), and the ps3recomp issue search for "strikeforce" returned 0. ### 1. ps3recomp and the ecosystem
- **KNOWN.** https://github.com/sp00nznet/ps3recomp.
  - Maintainer: sp00nz / Ned Heller (commit authors in git log).
  - About 746 stars; last push 2026-11-22. v0.20.0 = "111 PRs from sixteen contributors" (release https://github.com/sp00nznet/ps3recomp/releases/tag/v0.20.0).
  - It is a static recompiler, not an emulator: PPU (PowerPC64+VMX) and SPU code is lifted to C/C++ and linked with an HLE runtime of PS3 libraries (README "How It Works"; P/docs/PPU_RECOMP.md).
  - Windows render backend is D3D12, with Vulkan building on Windows (#746); Metal on macOS. Only Windows "runs a recompiled game, in this tree" (README platform table).
- **KNOWN.** Upstream port table (README, as of 2026-10-12):
  - "In game": The Simpsons Arcade Game (NPUB30563, playable and online) and Tornado Outbreak (BLUS30371).
  - Earlier partial ports: VF5, Tokyo Jungle, YDKJ, Twisted Metal, flOw.
  - Community repos on GitHub (descriptions are self-reported, not verified): Demon's Souls (https://github.com/timboat/demons-souls-recomp), Ratchet & Clank ToD (https://github.com/Re-TeRo17/ratchet-tod-recomp), Killzone 2/3 "partly playable" (https://github.com/undecuple/project-pyrrhus, https://github.com/undecuple/project-helghast), inFAMOUS 2, GoW Ascension, GT5, Drakengard 3, and others.
- **KNOWN.** Build pipeline (README "Getting Started"):
  - Needs Python 3.10+, CMake 3.20+, Ninja, and **clang-cl with VS2022 on Windows** ("plain MSVC builds the runtime library, but lifted game code needs clang-cl").
  - Steps: `ppu_loader.py` → `ppu_lifter.py --functions … --hle-stubs …` → `gen_hle_nids.py --all` → `cmake -G Ninja` in `templates/project`.
  - Each release also ships a prebuilt SDK zip per OS.
- **KNOWN.** Sister projects of the same kind:
  - N64Recomp https://github.com/N64Recomp/N64Recomp (push 2026-11-03)
  - XenonRecomp https://github.com/hedge-dev/XenonRecomp (push 2025-08-04)
  - PS2Recomp https://github.com/ran-j/PS2Recomp (push 2026-11-24)
  - ps3recomp's `tools/compare/` matches functions between the Xbox 360 (XenonRecomp/rexglue) build and the PS3 build of the same game (P/tools/compare/README.md).
- **KNOWN.** Limitations:

### 3. NIDs
- **KNOWN.** NID = first 4 bytes of SHA-1(name ‖ `67 59 65 99 04 25 04 90 56 64 27 49 94 89 74 1A`), read little-endian (R/rpcs3/Emu/Cell/PPUModule.cpp#L58-L75).
- **KNOWN.** NID databases:
  - RPCS3 `REG_FUNC` registrations in `rpcs3/Emu/Cell/Modules/*.cpp`.
  - ps3recomp `tools/nid_database.py` ("2000+ NID-to-name mappings from RPCS3 and Sony SDK", P/docs/TOOLS.md#L494) and `tools/nid_from_protos.json`.
  - The psdevwiki library pages.

### 4. Code discovery
- **KNOWN.** ps3recomp uses the `.opd` table as "an authoritative list of every address-taken function" (P/docs/TOOLS.md#L72-L75), plus jump-table recognition (`mtctr`+`bctr`, TOOLS.md#L216-L217).
- **KNOWN.** At runtime, `ps3_indirect_call` dispatches through a guest→host hash table and logs `[ppu] unresolved indirect call` for targets that were not lifted (TOOLS.md#L260; ppu_loader.cpp#L3176).
- **ASSUMED.** "Coverage-guided" discovery is possible: record executed PCs in RPCS3 with `tools/rpcs3_probe/trace.py`, then feed the missing addresses back to the lifter. I found no doc describing that loop. Its limit: it only finds code that actually ran.

### 5. RSX / SPU
- **KNOWN.**
  - RSX: the cellGcm FIFO is parsed into a shared draw engine, which runs the game's real NV4097 vertex and fragment programs on D3D12, Vulkan or Metal (README; P/docs/RSX_GRAPHICS.md).
  - SPU: SPU images are extracted and lifted to C, with an SPU interpreter fallback and hand-written PPU-side replacements (P/docs/SPU_LIFTER.md, P/docs/SPU_FALLBACK.md).
  - SPURS: it can run Sony's real `libsre.prx`, lifted LLE, instead of HLE (P/docs/FIRMWARE_LLE.md).
- **ASSUMED.** Reusing RPCS3's SPU recompiler code directly is not what ps3recomp does. Its README says "RPCS3 is a behavioural reference, not a code source".

## 1. HLE struct audit: ps3recomp vs RPCS3

### 1.1 cellVideoOut
- **KNOWN mismatch: `CellVideoOutDeviceInfo`.** This confirms Salem's finding.
  - RPCS3 layout: `colorInfo` (20 bytes) at +0x0C, `availableModes[32]` at +0x20, then `ksvList`. Total 456 bytes. Source: R `rpcs3/Emu/Cell/Modules/cellVideoOut.h#L184-L196`.
  - ps3recomp layout: no `colorInfo` and no `ksvList`. The modes start at +0x0C. Total 268 bytes. Source: P `libs/video/cellVideoOut.h#L120-L129`.
  - The writer is P `libs/video/cellVideoOut.c#L182-L233`. It also never sets each mode's `refreshRates`.
  - RPCS3 fills: latency 100, colorInfo 0xFFFF, gamma 100, and `refreshRates = 60HZ|59_94HZ`. Source: R `rpcs3/Emu/Cell/Modules/cellVideoOut.cpp#L288-L330`.
  - The NID checks out: SHA-1 of `cellVideoOutGetDeviceInfo` with the suffix gives `0x1E930EEF`, the same number Salem quoted.
- **KNOWN match:** `CellVideoOutState` (16 bytes), `CellVideoOutConfiguration` (16) and `CellVideoOutResolution` (4) have the same layouts. ps3recomp's `state=0` equals RPCS3's `CELL_VIDEO_OUT_OUTPUT_STATE_ENABLED`. Source: R `cellVideoOut.h#L104`.
- HOW TO VERIFY Salem's fix: if `refreshRates` is still 0 in his build, compare it against RPCS3's values above.

### 1.2 cellAudioOut: two KNOWN mismatches
These are the same class of bug as VideoOut, and they are the strongest candidates.

- **`cellAudioOutGetDeviceInfo` (NID 0x7663E368)**
  - RPCS3 layout:
    - `CellAudioOutSoundMode` is 8 bytes: type, channel, fs, reserved, `be u32 layout`.
    - `CellAudioOutDeviceInfo` has portType/availableModeCount/state/reserved[3] at +0..+5, `be u16 latency` at +6, and `availableModes[16]` at +8. Total 136 bytes.

## 4. Is `SPU_INTERP_UNLIFTED=1` safe?
- **KNOWN:** it triggers only when no lifted function exists, there is no policy mode, `pc >= 0x15000`, and the first word at the target is nonzero. In that case it runs `spu_interp_run` instead of stopping the job (P `runtime/spu/spu_channels.c#L2925-L2975`).
  - The source says it is opt-in "so titles that reach here on a genuinely bad pc keep the loud stop".
  - **So with it on, a bad PC that points at nonzero bytes gets interpreted instead of stopping. It can hide a different bug, and a later failure can show up far from its cause.**
- **KNOWN limits** (P `docs/SPU_INTERPRETER_LIFTED_HANDOFF.md#L68-L86`):
  - There is an unrepaired initial-call boundary (`bisl` → `spu_indirect_branch` before `spu_drain_call`).
  - Recursion matches on PC only.
  - An interpreted stop code 0 can be misclassified as failure.
  - Nonzero interpreted stops and halts "do not necessarily hard-unwind the outer driver".
  - "It does not establish that this change alone resolves a title's wait, completes its jobs, or produces rendering."
  - The interpreter is slower than lifted code (P `docs/GETTING_STARTED.md#L240-L245`).
- HOW TO VERIFY that it is benign for this game:
  - Count the `[spu] img=… interpreting unlifted LS 0x…` lines and check which images they come from.
  - If a different LS address shows up at Loading, that code is runtime-loaded, and the clean fix is to lift that image too.

## 2. Flow

### Sysutil event values (R `cellOskDialog.h#L21-L30`, KNOWN)

Input field results (R `#L32-L38`): OK 0, CANCELED 1, ABORT 2, NO_INPUT_TEXT 3.

### RPCS3 flow (KNOWN)
1. `LoadAsync` validates its arguments: non-NULL param, info, message and init_text, and `limit_length ≤ 512` (R `cellOskDialog.cpp#L235-L238`).
2. It copies init_text as the starting text, creates the dialog, and sends **LOADED** (R `#L648-L649`). In separate-window mode it also sends DISPLAY_CHANGED.
3. When the user confirms, `on_osk_close` sets result OK and sends **FINISHED** (R `#L408-L411`). In continuous separate-window mode it sends INPUT_ENTERED or INPUT_CANCELED instead (R `#L380-L391`).
4. `UnloadAsync` writes the result and the UTF-16 text, then sends **UNLOADED** (R `#L744-L745`).
5. `sysutil_send_system_cmd` queues the event to **every registered sysutil callback** (R `rpcs3/Emu/Cell/Modules/cellSysutil.cpp#L268-L311`).
6. If no dialog can be created, LoadAsync returns BUSY (R `#L126-L169`, `#L245-L249`).

ASSUMED: RPCS3 has no "auto-return" path in this code. A user (or the RPCS3 overlay) must confirm.

### ps3recomp flow
- **Stub (the Windows default)** fires **no events at all**: no LOADED, FINISHED or UNLOADED. It also returns early unless Init was called (section 0).
  - Even if Init were called, a game that waits for FINISHED before calling UnloadAsync would wait forever (ASSUMED behaviour of a typical title).
  - UnloadAsync/GetInputText write big-endian UTF-16 one unit at a time (P `#L203-L211`). The text is the empty string unless init_text or a default exists.
- **Native path (non-Windows only)** does LOADED → FINISHED → UNLOADED. Events are queued to all 4 slots from the guest's own `cellSysutilCheckCallback` poll (P `libs/misc/osk_native.c` `cellOskDialog_tick`; P `libs/system/cellSysutil.c#L216-L235`, `#L74-L85`).

## 3. Fastest fix: a minimal auto-confirm OSK

**This is a SKETCH, NOT TESTED.** It replaces the stub bodies in `libs/misc/cellOskDialog.c`. It is modelled on RPCS3's order of events and on ps3recomp's own native path. Offsets are from section 1.

Behaviour:
- LoadAsync takes no Init, validates like RPCS3 and queues **LOADED**.
- **FINISHED** is queued on a *later* `cellSysutilCheckCallback` poll, so the title sees LOADED and FINISHED on different polls the way a human would produce them.
- UnloadAsync writes the result and text, then queues **UNLOADED**.
- The name comes from the new env var `OSK_AUTO_TEXT` (**does not exist in ps3recomp; this sketch adds it**), else the game's init_text, else "Saud".

```c
/* ---- SKETCH: auto-confirm OSK for the Windows stub path (verify!) ---- */
#include "../system/cellSysutil.h"      /* cellSysutilQueueEvent, cellSysutil_set_osk_pump,
                                           CELL_SYSUTIL_MAX_CALLBACKS (P cellSysutil.h L90/L131/L135) */
#include <stdlib.h>
#define OSK_EV_LOADED    0x0502u   /* R cellOskDialog.h L23 */
#define OSK_EV_FINISHED  0x0503u   /* L24 */
#define OSK_EV_UNLOADED  0x0504u   /* L25 */
#define OSKDLG_ERR_PARAM 0x8002B504u /* R L17 */
#define SYSUTIL_ERR_BUSY 0x8002B105u /* R cellSysutil.h L55 */

static int s_auto_state = 0;   /* 0 free, 1 loaded (FINISHED pending), 2 finished */
static int s_auto_polls = 0;
static s32 s_auto_result = 0;  /* CELL_OSKDIALOG_INPUT_FIELD_RESULT_OK */

static void osk_broadcast(u32 status)
{
    printf("[cellOskDialog] auto: status=0x%X\n", status);
    for (int slot = 0; slot < CELL_SYSUTIL_MAX_CALLBACKS; slot++)
        cellSysutilQueueEvent(slot, status, 0);   /* drain skips unregistered slots */
}

/* Runs at the top of every cellSysutilCheckCallback (P cellSysutil.c L216-L235). */
static void osk_auto_pump(void)
{
    if (s_auto_state == 1 && ++s_auto_polls >= 2) {  /* not on the same poll as LOADED */
        s_auto_state = 2;
        osk_broadcast(OSK_EV_FINISHED);
    }
}

s32 cellOskDialogLoadAsync(u32 container, const CellOskDialogParam* dialogParam,
                           const CellOskDialogInputFieldInfo* inputFieldInfo)
{
    (void)container;
    u32 p_ea = GUEST_EA(dialogParam), i_ea = GUEST_EA(inputFieldInfo);
    if (!p_ea || !i_ea) return (s32)OSKDLG_ERR_PARAM;
    u32 msg_ea  = vm_read32(i_ea + 0);   /* message   */
    u32 init_ea = vm_read32(i_ea + 4);   /* init_text */
    u32 limit   = vm_read32(i_ea + 8);   /* limit_length */
    if (!msg_ea || !init_ea || limit > 512) return (s32)OSKDLG_ERR_PARAM;  /* R L235-L238 */
    if (s_auto_state != 0) return (s32)SYSUTIL_ERR_BUSY;                    /* R L245-L249 */
    if (limit >= 512) limit = 511;                                         /* R L253 */

    const char* forced = getenv("OSK_AUTO_TEXT");          /* NEW, sketch only */
    memset(s_result_text, 0, sizeof(s_result_text));
    if (forced && *forced) {
        osk_ascii_to_utf16(forced, s_result_text, limit);
        s_result_length = 0; while (s_result_text[s_result_length]) s_result_length++;
    } else {
        s_result_length = osk_guest_utf16(init_ea, s_result_text, limit);
        if (!s_result_length) { osk_ascii_to_utf16("Saud", s_result_text, limit); s_result_length = 4; }
    }
    s_auto_result = 0;     /* INPUT_FIELD_RESULT_OK */
    s_auto_state = 1; s_auto_polls = 0;
    s_osk_loaded = 1;
    cellSysutil_set_osk_pump(osk_auto_pump);
    osk_broadcast(OSK_EV_LOADED);                            /* R L648-L649 */
    return CELL_OK;
}

/* Shared by Unload/GetInputText; R getText L661-L770. */
static s32 osk_auto_text(u32 ea, int unloading)
{
    if (!ea) return (s32)OSKDLG_ERR_PARAM;
    s32 cap = (s32)vm_read32(ea + 4);        /* numCharsResultString = CAPACITY (input) */
    if (cap < 0) return (s32)OSKDLG_ERR_PARAM;
    if (s_auto_state == 0) return (s32)0x8002B302u; /* CELL_MSGDIALOG_ERROR_DIALOG_NOT_OPENED (R cellMsgDialog.h L21) */
    s32 result = unloading ? s_auto_result : (s_result_length ? 0 : 3);
    vm_write32(ea + 0, (u32)result);
    u32 str = vm_read32(ea + 8);
    if (str && result == 0) {
        u32 n = s_result_length < (u32)cap ? s_result_length : (u32)cap;
        if (n > 511) n = 511;
        for (u32 i = 0; i < n; i++) vm_write16(str + i * 2, s_result_text[i]);  /* BE UTF-16 */
        if (n < 511) vm_write16(str + n * 2, 0);  /* RPCS3 writes the 0 at index min(len,cap) (R L703-L716) */
    }
    /* do NOT write +4 (RPCS3 never does) */
    if (unloading) { s_auto_state = 0; s_osk_loaded = 0; osk_broadcast(OSK_EV_UNLOADED); }  /* R L744-L745 */
    return CELL_OK;
}
s32 cellOskDialogUnloadAsync(CellOskDialogCallbackReturnParam* r) { return osk_auto_text(GUEST_EA(r), 1); }
s32 cellOskDialogGetInputText(CellOskDialogCallbackReturnParam* r) { return osk_auto_text(GUEST_EA(r), 0); }

    s_auto_state = 2;

    return CELL_OK;
}
```

## 1. What a loader's SPURS task can block on, and the RPCS3 reference

RPCS3 runs the **real libsre** by default:
- `g_prx_list` "should hle if 1" has `libsre.sprx` = 0 (R `rpcs3/Emu/Cell/lv2/sys_prx.cpp#L31-L32`, `#L115`, use at `#L226`).
- So the SPU-side behaviour in a default RPCS3 run comes from Sony's own kernel plus RPCS3's SPU/MFC emulation (`SPUThread.cpp`).
- `cellSpursSpu.cpp` is RPCS3's HLE version of that kernel. ps3recomp's HLE mirrors it (its comments cite it, e.g. D `spu_channels.c#L2387-L2395`).

### a) SPURS event flag (PPU waits, SPU task sets, or the other way round)
- **SPU side:** the task updates the flag line with GETLLAR/PUTLLC, then blocks via the taskset syscall `WAIT_SIGNAL` (`stop`/branch to the PM syscall entry, LS 0xA70 in ps3recomp's HLE).
- **PPU side:** `cellSpursEventFlagWait` / `cellSpursEventFlagSet`.
- **RPCS3:**
  - `cellSpursEventFlagSet` (R `rpcs3/Emu/Cell/Modules/cellSpurs.cpp#L3329-L3463`)
  - `_spurs::event_flag_wait` (`#L3464-L3618`) and `cellSpursEventFlagWait` (`#L3620`)
  - the SPU-side syscall in `spursTasksetProcessSyscall` (R `rpcs3/Emu/Cell/Modules/cellSpursSpu.cpp#L1868-L1975`, WAIT_SIGNAL at `#L1913`)
- **ps3recomp:**
  - PPU `cellSpursEventFlagWait` polls every 2 ms and prints `[cellSpurs] EventFlagWait BLOCKED tid=… Ns on pattern 0x…, flagEA=0x… -- waiting for an SPU …` about once a second (D `libs/spurs/cellSpurs.c#L2523-L2609`, print at `#L2571`).
  - SPU WAIT_SIGNAL is in D `spu_channels.c#L2396-L2465`, which calls `spu_taskset_wait_signal` (D `spu_workload.c#L1503-L1600`; it prints `task N (taskset 0x…) sleeping Ns in WAIT_SIGNAL`).

### b) Taskset signal
- **SPU side:** `WAIT_SIGNAL` (syscall 2) or `POLL` (3).
- **PPU side:** `cellSpursSendSignal` / `_cellSpursSendSignal`.
- **RPCS3:** `_cellSpursSendSignal` (R `cellSpurs.cpp#L4252`); requests `SPURS_TASKSET_REQUEST_*` in `spursTasksetProcessRequest` (R `cellSpursSpu.cpp#L1306-L1313`, `#L1413-L1624`).

  - `cellSpursSendSignal` (D `cellSpurs.c#L1620`) and `_cellSpursSendSignal` (`#L2704`) lead to `spu_taskset_signal_task` (D `spu_workload.c#L1405`).

- The queue is driven by the event flag plus signal on the SPU side.

### g) sys_event_port / spu_thread_send_event, and receive

### h) Task yield/exit and other taskset syscalls
- **RPCS3:** `spursTasksetProcessSyscall` handles EXIT, YIELD, WAIT_SIGNAL, POLL and RECV_WKL_FLAG with real state changes (R `cellSpursSpu.cpp#L1868-L1975`); dispatch is `spursTasksetDispatch` (`#L1740`).
- **ps3recomp: KNOWN gap.** The HLE syscall handler gives **only WAIT_SIGNAL real semantics**. EXIT halts the task. **YIELD, POLL and RECV_WKL_FLAG just "report success and resume"** (D `spu_channels.c#L2467-L2470`).
  - ASSUMED: a task that polls for a workload flag or waits to be rescheduled never sees the state it expects.
- **ps3recomp: KNOWN asymmetry.**

- **Barrier / semaphore:** RPCS3 has `cellSpursBarrierInitialize` (R `cellSpurs.cpp#L5368`); `_cellSpursSemaphoreInitialize` is a stub (`#L5405`). ps3recomp has `cellSpursBarrierInitialize` (D `cellSpurs.c#L4053`).

### Documented scheduler limits (KNOWN, D `docs/SPURS_SCHEDULING.md#L45-L50`)
- There is no preemption.
- "A blocked workload still requires an available physical slot for its producer".
- Guest code that never returns cannot be cancelled.

## 5. Out-of-the-box options (ranked by effort, lowest first)

**(b) Memory snapshot diff. Lowest effort, diagnosis only.**
- KNOWN: both programs keep guest memory as one flat block in the host process. RPCS3 reserves it at `g_base_addr` (hint 0x2'0000'0000; R `rpcs3/Emu/Memory/vm.cpp#L43`). ps3recomp has `vm_base` from `VirtualAlloc(VM_SIZE=0x100010000)` (D `templates/project/main.cpp#L167`, `#L327`).
- A full process dump of each (Task Manager live dump or WinDbg `.dump /ma`) contains the guest RAM. Use WinDbg `.writemem` to extract a range.
- ASSUMED: heap addresses will differ between the two (different allocators: ps3recomp has its own `sys_memory.c` pool), so a whole-RAM diff will be noise.
- Diff **objects** instead: the taskset at its EA (RPCS3 `CellSpursTaskset` running/ready/enabled/signalled bitsets, layout in R `rpcs3/Emu/Cell/Modules/cellSpurs.h`), the event flag at the `flagEA` from the BLOCKED line, and the loader's own state struct (found from the PPU waiter's stack).
- Its value is pinpointing *which* flag or bit is missing. It does not fix anything by itself.

**(a) Record and replay. Medium-high effort, fragile.**
- KNOWN: RPCS3 "MFC Debug" records only a ring of the **last 4096** MFC commands per SPU, with ≤128 B of data each (R `SPUThread.h#L824-L826`, `MFC.h#L103-L108`). That is not a full record of a loading task's PUT data, so a custom (local) RPCS3 build would be needed to log every PUT/PUTLLC with its payload.
- ASSUMED blockers:
  - target EAs differ between RPCS3 and ps3recomp heaps, so writes need to be relocated by object;
  - the task's output depends on file contents and timing;
  - it handles only this load, not the next stage;
  - it would also have to fake the sync side effects (event flag/signal) that the PPU waits on.
- A one-off "replay the final flag write" is basically the documented `SPURS_EF_SPU_REPLY` / `SPURS_EF_FORCE` diagnostic, which the source itself labels "DIAGNOSTIC BISECT, NOT A FIX" (D `spu_channels.c#L2408-L2422`; `SPURS_EF_FORCE` at D `cellSpurs.c#L2547-L2549`, `#L2581`). That is a cheap way to test the idea.

**(c) Hybrid: reuse RPCS3's SPU interpreter/recompiler. Highest effort, low payoff.**
- **Licence (KNOWN):** RPCS3 is GPL-2.0 (R `LICENSE`) and ps3recomp is MIT (D `LICENSE`). The FSF lists Expat/"MIT" as GPL-compatible (https://www.gnu.org/licenses/license-list.html#Expat). The GPL lets you make and use modified versions privately without releasing them, but anything you release must come with source under the GPL (https://www.gnu.org/licenses/gpl-faq.html#GPLRequireSourcePostedPublic).
  - So a private, local GPL-combined build is allowed. A distributed binary would have to be GPL as a whole.
- **ps3recomp policy (KNOWN):** "No RPCS3 (GPL) code belongs in this tree" (D `README.md#L399`) and "Don't port code from GPL projects … copying or translating its code into ps3recomp is not [encouraged], even rewritten line by line" (D `CONTRIBUTING.md#L258-L264`). It can never go upstream.
- **Payoff (ASSUMED):** ps3recomp **already has** its own SPU interpreter (D `runtime/spu/spu_interp.c`). The gaps found above are in SPURS/taskset syscall servicing and channel blocking, not in instruction decoding. RPCS3's interpreter is also tied to its `spu_thread`/vm/cpu_thread classes. So a lot of integration work would fix the wrong layer.

**Overall:** lifting the image (§2.5) plus rebasing to e85647a is cheaper than all three. Use (b) only if a lifted task still hangs.

## 1. Layouts (all big-endian; KNOWN from R `rpcs3/Emu/Cell/Modules/cellSpurs.h` CHECK_SIZE asserts)

Task bitsets are 4 BE u32. **Task t = bit (31 - t%32) of word t/32**, so task 0 is the MSB of byte 0 (R `cellSpurs.h#L1050-L1058`). ps3recomp uses the same order (P `libs/spurs/spurs_taskset.h#L77-L96`).

| 0x68 | 8 | args | |
| 0x70 | 1 | enable_clear_ls | |

The bitset rules are in RPCS3's HLE kernel (R `cellSpursSpu.cpp`):
- Valid-state check (`#L1432-L1437`): waiting∧running = 0, ready∧pending = 0, enabled ⊇ others.
- YIELD sets waiting and clears running (`#L1470-L1475`).
- WAIT_SIGNAL, when no signal is pending, sets waiting and clears running and ready (`#L1476-L1487`).
- DESTROY clears running and enabled (`#L1461-L1468`).

These rules are HLE code. With default LLE libsre, RPCS3 runs Sony's kernel. ASSUMED: the same struct semantics, since the HLE was modelled on it.
